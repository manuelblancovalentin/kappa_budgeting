# Backend Template Passes
<PageMeta />
---

<TBox type="summary" title="Role">

Forward firmware calls are already generated by backend template passes. Backward firmware should use the same mechanism.

</TBox>

## What hls4ml Does Today

hls4ml templates are optimizer passes. The base classes are in `hls4ml/backends/template.py`:

| Class | Attribute generated |
|---|---|
| `LayerConfigTemplate` | `config_cpp` |
| `FunctionCallTemplate` | `function_cpp` and `include_header` |

For example, Vivado dense forward code is defined in `backends/vivado/passes/core_templates.py`:

```text
DenseConfigTemplate
  -> struct configN : nnet::dense_config { ... }

DenseFunctionTemplate
  -> nnet::dense<input_t, output_t, configN>(input, output, w, b);
```

Convolution templates follow the same pattern, but may generate multiple config structs such as a convolution config plus a nested/mult config.

The writer does not know the meaning of dense or convolution. It emits whatever `config_cpp`, `function_cpp`, and headers the passes attach.

## What Training Should Add

Create parallel template classes for trainable code:

```text
DenseBackwardConfigTemplate
DenseBackwardFunctionTemplate
Conv1DBackwardConfigTemplate
Conv1DBackwardFunctionTemplate
Conv2DBackwardConfigTemplate
Conv2DBackwardFunctionTemplate
ActivationBackwardFunctionTemplate
ReshapeBackwardFunctionTemplate
PoolingBackwardFunctionTemplate
BatchNormalizationBackwardConfigTemplate
BatchNormalizationBackwardFunctionTemplate
```

These should attach different attributes so they do not interfere with forward code:

```text
backward_config_cpp
backward_function_cpp
backward_include_header
```

The writer can then emit forward code and backward code separately.

## Required Static Headers

The deprecated fork already had useful kernel headers under `templates/vivado/autograd` and `templates/vivado/losses`. In the new fork, these should be copied as static firmware assets:

| Header group | Purpose |
|---|---|
| `autograd/nnet_dense_backprop.h` | Dense gradient and update code. |
| `autograd/nnet_conv_backprop.h` | Convolution gradient and update code. |
| `autograd/nnet_activation_backprop.h` | Activation gradient transport. |
| `autograd/nnet_common_backprop.h` | Reshape/flatten common backpasses. |
| `autograd/nnet_pooling_backprop.h` | Pooling backpasses. |
| `autograd/optimizers.h` | SGD/Adam/update helper code. |
| `autograd/controller.h` | New home for global throttle controller code. |
| `losses/*.h` | Loss and initial gradient computation. |

The static headers should be generic and template-driven. Per-model constants and typedefs should come from generated config structs.

## Backward Function Shape

For a dense layer, the generated call should be resolved by the template pass:

```cpp
nnet::dense_backpass<configN>(
    grad_in,
    grad_out,
    data_in,
    weight,
    bias,
    apply_update,
    batch_info,
    controller_state
);
```

The exact signature may change, but the important rule is that the pass decides the arguments using layer attributes, not by parsing existing C++.

## What Not To Do

Do not make the Vivado writer:

- inspect layer class names to decide backpass headers;
- regex-edit `config_cpp`;
- infer previous layer outputs;
- infer loss endpoints;
- synthesize optimizer typedefs;
- calculate controller state layout.

Those are pass/template responsibilities.
